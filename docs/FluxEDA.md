# FluxEDA 五层协议架构：可执行步骤拆分

根据论文描述，FluxEDA采用五层架构，将异构EDA工具整合到统一的API空间中。以下针对每一层协议拆分到具体可执行步骤。

***

## 一、访问层

**职责**：为上层Agent和可编程客户端提供统一入口

| **步骤** | **操作** | **具体内容**                                               |
| ------ | ------ | ------------------------------------------------------ |
| A1     | 选择访问方式 | 通过MCP Server（面向Agent）、Python SDK或C++ SDK（面向编程客户端）发起请求  |
| A2     | 封装请求   | 调用客户端SDK，将目标方法名、参数列表、执行元数据打包                           |
| A3     | 路由至通信层 | SDK/MCP Server将封装后的请求转发至公共通信路径                         |

**关键约束**：上层客户端不直接接触任何EDA工具的shell，所有请求必须经Access层统一封装

***

## 二、通信层

**职责**：跨RPC边界的结构化消息传递

| **步骤** | **操作**  | **具体内容**                                                                   |
| ------ | ------- | -------------------------------------------------------------------------- |
| C1     | 构造RPC消息 | 将请求打包为结构化的socket-based RPC消息，包含target method、arguments、execution metadata  |
| C2     | 会话管理    | Session Manager将RPC消息与当前会话的`instance_id`关联，确保路由到正确的后端实例                    |
| C3     | 转发至网关   | RPC Client将消息送入Gateway控制阶段                                                 |
| C4     | 响应回传    | 网关处理完成后，结构化响应沿原路径返回调用者                                                     |

**关键数据结构**：

* 每个RPC携带唯一`request_id`（用于调用追踪、响应匹配、错误报告）
* `instance_id`作为路由句柄，在多次调用间保持不变

***

## 三、网关层

**职责**：执行前控制检查、能力发现、方法分发

### 阶段1：执行前控制检查（Pre-execution Control）

| **步骤** | **操作** | **具体内容**                                       |
| ------ | ------ | ---------------------------------------------- |
| G1     | 协议验证   | 校验RPC消息格式是否符合通信契约                              |
| G2     | 注册表查找  | 在已注册的`api_*`方法表中查找请求的目标方法；**拒绝未注册的任意shell过程**  |
| G3     | 参数检查   | 验证传入参数的类型、数量、范围是否匹配方法签名                        |
| G4     | 能力级授权  | 检查调用者是否具备调用该方法的权限                              |

### 阶段2：能力发现

| **步骤** | **操作** | **具体内容**                                                |
| ------ | ------ | ------------------------------------------------------- |
| G5     | 自省查询   | 客户端通过`api_ping`检查连通性，通过`api_list_method`查询可用方法列表及接口元数据  |
| G6     | 按需获取详情 | 仅在需要时查询具体方法的调用要求（渐进式功能暴露，避免上下文预算浪费）                     |

### 阶段3：方法分发

| **步骤** | **操作** | **具体内容**                                 |
| ------ | ------ | ---------------------------------------- |
| G7     | 路由分发   | 将验证通过的可执行请求分发到对应的通用API或工具特定API           |
| G8     | 结果规范化  | 后端执行完成后，沿post-gateway路径对结果进行规范化处理        |
| G9     | 构造响应   | 根据所选返回模式，构造包含状态信息、类型化数据/文本输出/原始工件的结构化响应  |

**安全边界**：网关仅解析显式注册的`api_*`方法，为后端访问定义清晰的执行边界

***

## 四、EDA工具适配层

**职责**：通过一致的可调用接口暴露原生工具功能

| **步骤** | **操作** | **具体内容**                                                     |
| ------ | ------ | ------------------------------------------------------------ |
| T1     | 方法注册   | 为每个EDA工具（时序分析、综合、仿真、物理实现等）注册`api_*`方法，封装工具原生功能               |
| T2     | 语义适配   | 将统一的API调用翻译为工具特定的命令语义（不同工具的命令语义、状态模型、报告格式差异被限制在`api_*`方法之后）  |
| T3     | 调用后端实例 | 将适配后的操作发送至Runtime Management层维护的后端实例执行                       |
| T4     | 输出解析   | 将工具原生输出（报告、日志、数据）解析并规范化为结构化返回格式                              |

**设计原则**：不消除工具特定行为，而是将其封装在统一接口之后

***

## 五、运行时管理层

**职责**：后端实例的全生命周期管理，维持持久化执行状态

### 阶段1：实例创建与绑定

| **步骤** | **操作** | **具体内容**                           |
| ------ | ------ | ---------------------------------- |
| R1     | 进程启动   | 启动EDA工具进程，纳入运行时管理                  |
| R2     | 端口分配   | 为新实例分配通信端口                         |
| R3     | 就绪检查   | 等待工具进程初始化完成，确认可接受请求                |
| R4     | 实例绑定   | 将进程绑定到唯一`instance_id`，作为后续调用的路由句柄  |

### 阶段2：会话维护

| **步骤** | **操作** | **具体内容**                        |
| ------ | ------ | ------------------------------- |
| R5     | 请求路由   | 根据`instance_id`将请求路由到对应的后端实例    |
| R6     | 状态保持   | 同一实例在多次请求间保持已加载设计、执行上下文和中间状态不变  |
| R7     | 心跳监控   | 通过heartbeat-based机制维护会话活性       |
| R8     | 长任务支持  | 对长时间运行的操作提供异步执行支持               |

### 阶段3：实例回收

| **步骤** | **操作** | **具体内容**         |
| ------ | ------ | ---------------- |
| R9     | 超时控制   | 请求超时或会话空闲超时触发清理  |
| R10    | 故障处理   | 检测实例故障，执行清理与可选重启 |
| R11    | 显式释放   | 客户端显式释放实例时，回收资源  |

***

## 端到端请求路径总览

```
Agent/Client
    │
    ▼ [A1-A3] 访问层：选择入口、封装请求、转发
    │
    ▼ [C1-C3] 通信层：构造RPC消息、关联instance_id、转发至网关
    │
    ▼ [G1-G4] 网关层(控制)：协议验证→注册表查找→参数检查→授权
    │         (如需) [G5-G6] 能力发现：api_ping / api_list_method
    │
    ▼ [G7] 网关层(分发)：路由到对应api_*方法
    │
    ▼ [T1-T2] 适配层：方法注册查找→语义适配
    │
    ▼ [R5-R6] 运行时层：路由到instance_id对应的活实例→执行
    │
    ▼ [T4] 适配层：输出解析与规范化
    │
    ▼ [G8-G9] 网关层(后处理)：结果规范化→构造结构化响应
    │
    ▼ [C4] 通信层：响应回传
    │
    ▼ 原调用者收到 typed data / text output / raw artifacts
```

***

## Skills层的角色

Skills层独立于上述五层，作为**工作流知识编码层**运行：

| **要素**  | **内容**                    |
| ------- | ------------------------- |
| 任务分解    | 将高层设计意图拆解为可执行的api\_\*调用序列 |
| 输入验证    | 在调用前验证输入参数的业务合法性          |
| 执行顺序    | 规定功能组合的先后次序               |
| 会话上下文保存 | 在多步骤流程中维护上下文一致性           |
| 可重用模板   | 提供标准化的操作模板供Agent复用        |

**关注点分离原则**：MCP层控制"如何安全公开和管理工具功能"，Skills层规定"何时以及以何种顺序组合这些功能"

***

> **总结**：FluxEDA通过这五层协议的严格分层，实现了从Agent请求到EDA工具执行的完整可管控链路。核心区分点在于：`instance_id`维持实例连续性，`request_id`保证单次调用可观测性，`api_*`方法注册制确保执行边界安全，渐进式能力暴露避免上下文膨胀。
